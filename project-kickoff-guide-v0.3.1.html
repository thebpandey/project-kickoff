Turn one idea into an approved plan.

Project Kickoff is a skill for Codex and Claude Code. It asks one unresolved question at a time and records your answer. It writes the approved product, design, technical, and plan records, then prepares the Agent-Team handoff.

Important: Project Kickoff actions are chat messages. They are not shell commands. You type them into Codex or Claude Code, and the Skill never writes product feature code.

What Project Kickoff does

Think about a building permit office. You describe the building you want. The office asks one question at a time. It records each approved answer. You get approved drawings before anyone pours concrete. Project Kickoff works the same way for software.

Short version:
Answer one question.
Approve each stage.
Get approved records.
Hand the approved plan to Agent-Team.
  • QuestionsOne unresolved question per turn, with recommended choices and their trade-offs.
  • RecordsStable decision, requirement, and task IDs in the approved project documents.
  • PreparationOne live tracker, a minimal scaffold, and a validated handoff file.

Project Kickoff supports new and existing web, mobile, desktop, API, CLI, and library projects. For an existing project it audits first, then asks you to retain, change, or defer each finding. It does not repair or refactor product code, and it does not choose an unresolved stack, tracker, product, or design for you.

Install the complete package

Project Kickoff ships under a proprietary Private Use License. You need written permission from the licensors before you install it. The install examples use the GitHub CLI and the verified v0.3.1 release tag. Choose one host and one scope before you install.

ScopeCodexClaude Code
User~/.agents/skills/project-kickoff~/.claude/skills/project-kickoff
Project.agents/skills/project-kickoff.claude/skills/project-kickoff

  1. Check your access

    Get written permission from the licensors first. Sign in to the GitHub CLI with the account you will use. Use gh auth status to check that access. Never paste a token into chat.

  2. Open the intended project root

    Install the Skill into the repository where you will use it. Do not install it into an unrelated ancestor repository. The install block stops when an existing Git root does not match the current directory. For an empty new directory, the block creates the repository with a main branch.

    A nonempty directory without Git stops the block with Confirm and initialize this nonempty project first. Inspect the content. Confirm the intended root. Run git init -b main yourself. Then run the install block again.

  3. Ask the agent to install it

    Recommended install prompt
    Install the complete Project Kickoff package from https://github.com/thebpandey/project-kickoff. Use release tag v0.3.1 and my authorized GitHub access. Inspect the source, license, exact revision, and any existing installation first. Install it at the skill path for this actual host. Use project scope unless I name user scope. Keep the licensed Skill package out of the project's committed files. Check the package, then tell me which reload steps remain.

  4. Check the package contents

    The workflow reads its references and templates at run time. Do not install SKILL.md alone. Check that LICENSE, CHANGELOG.md, agents/openai.yaml, references/, assets/templates/, assets/hooks/, and scripts/ all arrived. Do not mix files from different release tags.

  5. Reload the host

    Codex reads repository skills under .agents/skills/. Claude Code reads them under .claude/skills/. Restart or refresh the host if the Skill does not appear. In Claude Code, a personal skill with the same name can shadow the project skill, so check the loaded source.

Release archive and optional hooks

The release archive is project-kickoff-0.3.1.zip. Install the complete extracted directory at one native host path. Check the archive against its release checksum when one is supplied.

Version 0.3.1 ships three optional hook scripts: a read-only session context loader, a direct-edit guard, and a read-only checkpoint advisory. Each one stays off until you approve and configure it for one project. Installing or upgrading the Skill does not change host settings and does not activate a hook. The hooks need Python 3.9 or later on a POSIX host. They use no third-party module.

Invoke the skill in your host

Use the prefix for your host. Type the action into the Codex or Claude Code chat. Do not run it in a shell.

Codex

Help
$project-kickoff help

Claude Code

Help
/project-kickoff help

The Skill accepts seven actions: start <idea>, audit [path], audit-only [path], resume [path], status [path], help, and version. It also accepts clear plain language. For example: Project Kickoff, show the status for this project.

Resume, status, help, and version

resume restores the recorded Skill version, decisions, approvals, the pending question, the setup receipt, and the next action. It inspects the real files before it trusts the checkpoint.

Continue a saved kickoff
$project-kickoff resume /absolute/path/to/project

status is read-only. It reports the loaded Skill version, the resolved project and revision, the current phase, the last approval, the pending question, blockers, and the next action. It does not write a checkpoint, replay the pending question, run setup, or run project tests.

Read the current phase
/project-kickoff status /absolute/path/to/project

version is read-only. It reports the package version, the loaded Skill path when that is available, and the matching CHANGELOG entry.

Check the loaded release
/project-kickoff version

If a read-only action gets an ambiguous or missing project path, the Skill reports the limit and shows how to supply the path. It does not turn the request into discovery.

The four states

A project moves through discovery, approved planning, setup, and ready for handoff. The Skill routes your action word before it enters any of them.

  1. Route the action. The Skill reads the action word first. A read-only action returns its report and stops there.
  2. Detect the mode. start checks for real product content. Installed skill folders and empty Git metadata do not count.
  3. Discovery. The Skill creates the checkpoint records and asks one unresolved question per turn.
  4. Approved planning. You approve each of the five stages on its own. The Skill then writes the approved documents.
  5. Setup. The Skill checks dependencies, activates one tracker, seeds the task IDs once, and delegates the minimal scaffold.
  6. Ready for handoff. The Skill validates the handoff file and prepares the exact Agent-Team invocation for your host.
A changed decision does not restart the project. The Skill marks the old decision superseded, finds the dependency edges, and invalidates only the affected approvals and derived sections. Unrelated approvals stay valid. It refreshes the affected artifacts after renewed approval.

Start a new project

Use start with one plain sentence about the idea. Name the intended project directory in the same turn or in your answer to the first question.

New project in Codex
$project-kickoff start Build a study planner for high-school students.

  1. Confirm the project boundary

    The Skill resolves the intended project path and the actual Git root. If the two differ, it reports the relationship and waits. It does not adopt an ancestor repository without your choice, and it does not write a checkpoint into an ambient parent repository.

  2. Let it detect the project mode

    Meaningful product content sends the request to the audit route. The Skill ignores its own installed folder under .agents/skills/ or .claude/skills/, empty Git metadata, and install-only housekeeping. An otherwise empty directory stays a new project.

  3. Answer the first question

    After the path is confirmed, the Skill creates .project-kickoff/DISCOVERY.md and keeps CONTEXT.md as the short resumption pointer. It then asks one question and waits for your answer.

  4. Approve each stage

    At the end of each stage, the Skill summarizes the confirmed decisions, assumptions, evidence, and open items. It then asks one separate approval question.

Worked example

You type $project-kickoff start Build a study planner for high-school students. The Skill confirms the project directory, creates .project-kickoff/DISCOVERY.md, and asks one product question, such as which student group the first release serves. It records your answer as DEC-001 with its source and date. It then asks the next unresolved question. It does not pick the stack, the design direction, or the tracker while a dependent choice is open.

Audit an existing project

Use the audit route when the directory already holds product code, project documents, configuration, a tracker, or real Git history. The audit starts read-only.

audit

Inspects the project, writes the approved audit records, and then continues through guided retain, change, and defer decisions into setup. This is the default.

Claude Code
/project-kickoff audit /absolute/path/to/project

audit-only

Performs the same bounded audit and stops after the report. Use it when you want evidence before you decide anything.

Codex
$project-kickoff audit-only /absolute/path/to/project

What the audit will not do

During the audit the Skill does not initialize Git, rename an existing branch, or replace project files. It also does not select a new tracker, install dependencies, or run mutating setup. It preserves all user work and all existing branches. It never overwrites, renumbers, closes, reopens, migrates, or duplicates tracker items. If the project evidence does not identify the canonical integration branch, the Skill asks you which existing branch it is.

What the report contains

Each finding gets a stable AUD-### ID with severity, the evidence path or revision, and the observed condition. The finding also records impact, confidence, the evidence gap, and a recommended decision. The Skill creates or merges root AUDIT.md and preserves existing findings and IDs. It reports every check as one of four states: run and passed, run and failed, blocked, or not run. Historical CI output and a README command are prior evidence. They are not a test result from this audit.

Worked example

You run audit on a two-year-old API project. The Skill records that the documented architecture names a message queue, and that the code calls the database directly. It files that gap as AUD-004 with the file path and the inspected revision. It then asks one question: keep the current direct calls, change to the documented queue, or defer the decision. The audit itself approves no remediation.

One question at a time

This is the behavior that separates Project Kickoff from a document generator. The Skill asks exactly one unresolved question per turn. It records that question as pending before it asks. It then ends its turn and waits.

If the host has no native choice control, the Skill sends exactly this plain-text shape and ends the turn.

The plain-text question shape
<One question>

1. <Choice> (Recommended) — <effect or trade-off>
2. <Choice> — <effect or trade-off>
3. <Choice> — <effect or trade-off>

Reply with a number or your own answer.

Two choices are enough when there are only two real options. A filled question looks like this.

The same shape with a real question
Which tracker do you want as the one live tracker?

1. Beads (Recommended) — dependency-aware task records that suit an Agent-Team handoff
2. Root TASKS.md — a simple single-writer file without Beads automation

Reply with a number or your own answer.

When the host exposes a native choice control, the Skill uses it. In Codex that is the exposed user-input tool. It carries one question, two or three mutually exclusive choices, and the recommended choice first. Its label contains (Recommended). The host supplies the free-text choice, so the Skill does not add a duplicate one. Free-text answers are always valid.

Silence is not an answer

A timeout or silence is not an answer. The Skill does not ask the next question, write a dependent decision, activate a fallback, or start setup until your answer arrives.

Five separate approvals

The five stages are product definition, first-release scope, experience and design, technical blueprint, and execution and handoff. Each stage ends with its own approval question, recorded as APR-001 through APR-005.

Decisions carry sources

Each material decision gets a DEC-### record with its source, date, status, rationale, and affected artifacts. Open assumptions and blockers stay marked as open. The Skill does not convert them into facts.

A change is an answer

An explicit change from you is recorded as the answer and the decision source. The Skill does not ask you to confirm that same decision again. It asks only for the next unresolved consequence.

Research-dependent choices. For a stack, architecture, or tracker question, the Skill first inspects the project evidence and current primary sources. It presents the alternatives, their material trade-offs, source links, and the check date. It recommends one choice based on your confirmed constraints. You select the answer.

What Project Kickoff writes

The Skill adapts the templates in assets/templates/. It does not overwrite an existing file. It inspects the file, keeps your content, and merges the approved additions. Each derived artifact records its source decision IDs, the generating Skill version, and the approved revision.

Stable IDs never change when a title or an order changes, and a retired ID is never reused for a new meaning. An existing project keeps its established IDs; the Skill does not renumber them to its own convention. Epics and stories stay in PLAN.md as EPIC-### and STORY-### summaries. They are not seeded as runnable tracker rows.

Discovery writes very little. While a dependent choice is open, the Skill limits its writes to .project-kickoff/DISCOVERY.md and CONTEXT.md. It also writes the explicitly approved .project-kickoff/context-hook.json activation marker and other planning notes you approved. It does not store credentials, raw sensitive data, or private reasoning in any checkpoint.

Setup and the minimal scaffold

Setup runs after the dependent product, scope, design, and technical decisions are approved. It changes only the selected project.

The six dependencies

The Skill presents these six every time, even when some are already ready. For each one it shows the purpose and a Ready, Missing, or Cannot use status. It also shows the selected executable or skill path, the source, and the version or exact revision. It ends with the install scope and location, the license or access terms, and the verification result.

  1. Resolve the Git boundary

    The Skill inspects the top level, status, remotes, branches, and worktrees. A new repository uses main as its canonical branch. An existing repository keeps its branch names, and the Skill records the branch that you designate.

  2. Check that each tool runs

    A directory, a download, or a successful installer exit is not proof that a tool works. The Skill uses the selected executable's version or help output and a small functional check. It prefers project scope and reuses a compatible installation.

  3. Select one tracker

    If Beads is unavailable, the Skill researches current free or open-source alternatives, includes root TASKS.md as one choice, and asks one question. It does not create, write, or call any fallback tracker before you select it.

  4. Seed the tracker once

    Seeding starts only after PLAN.md is approved. The Skill resolves each executable task from the saved mapping, creates a tracker item only when none exists, and persists each new mapping immediately. A failed run leaves a valid partial seed that the next run continues. It never deletes and recreates the tracker to recover.

  5. Build the minimal scaffold in a worktree

    The Skill keeps the canonical checkout for planning and shared records. It creates a task branch and worktree from the verified integration revision, and delegates all scaffold code, configuration, builds, and tests to that worktree. It combines the work in one integration worktree, verifies it, and then updates the canonical branch.

The scaffold is not an application. A minimal scaffold holds only the approved structure and basic tooling. The Skill lists commands only for tools that were created and verified, and it states plainly when no runnable application exists yet. It does not implement product features during kickoff.

Setup never changes global configuration, installs global hooks, or overwrites existing instructions without matching authority. It records every declined, deferred, failed, and superseded choice in .project-kickoff/setup.json. That receipt records choices. It grants no new permission.

Hand off to Agent-Team

Project Kickoff 0.3.1 handoffs are tested against Agent-Team 7.0.2. Kickoff supplies the approved documents, the selected tracker and its mapping, and the setup receipt. It also supplies the project instructions, the first ready task, and the validated handoff file.

  1. Meet the readiness gate

    The Skill declares ready for handoff only when every condition below is true. A failed install is not ready, and a deferred optional tool is reported separately.

    The readiness conditions
    • All five stage approvals are current, and no implementation-blocking decision is unresolved.
    • PRD.md, DESIGN.md, and PLAN.md agree on first-release scope, stack, architecture, requirement IDs, and acceptance criteria.
    • The scaffold matches the approved scope, and its actual checks pass.
    • Dependency receipt statuses are factual, and the required capabilities are ready.
    • Exactly one tracker is active, the mappings are complete, the dependencies are acyclic, and the first actionable task is known. An audit can instead establish that no implementation work remains.
    • AGENTS.md, CLAUDE.md, MISTAKES.md, CONTEXT.md, discovery, and tracker ownership agree.
    • No roadmap item was activated, and no feature implementation began.

  2. Write and validate the handoff file

    The Skill adapts the template to .project-kickoff/AGENT_TEAM_HANDOFF.json and runs the bundled checker against it. Resolve <project-kickoff-skill-path> to the loaded Skill directory. This one is a real shell command.

    Validate the handoff in a shell
    python3 <project-kickoff-skill-path>/scripts/check_agent_team_handoff.py \
  --handoff .project-kickoff/AGENT_TEAM_HANDOFF.json

  3. Start Agent-Team yourself

    The Skill prepares the exact invocation for the detected host. You send it.

    Codex
    $agent-team start
    Claude Code
    /agent-team start

The limits the checker enforces

The tracker must be Beads or Markdown at root TASKS.md or .agent-team/TASKS.md. The file holds at most 500 implementation task records and stays at or below 250 KiB, so Agent-Team can wrap it in its initialization request. Task IDs must be unique, safe, and an exact match for every row in the selected tracker. The task list holds only tracker task IDs.

Titles, status, and dependencies stay in the tracker and the approved plan. The file itself also carries the approved scope, the release acceptance conditions, the verification commands, and the owned paths. The approved plan revision must exist on the named integration branch, and the recorded project revision must equal the current branch tip. At least one dependency-ready task must exist while implementation work remains.

Project Kickoff prepares the command. It does not run it. The Skill never creates or edits .agent-team/setup.json. Agent-Team owns that runtime receipt and creates it during project initialization. Project Kickoff can read an existing one for audit or resume, and treats it as read-only.

After verified integration into the canonical integration branch, the Skill cleans the eligible task branches, worktrees, and task-owned processes. It checks each worktree by ancestry, or by exact patch identity for a squashed integration. It removes only clean, fully integrated worktrees through normal Git worktree commands, and it never forces a removal. Unknown files, local data, secrets, and unfinished changes are retained and reported. This cleanup does not wait for a production deployment.
